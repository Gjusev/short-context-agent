## Notes

- **staged-release/sac (the one asterisk).** The end state passed verify — all
  five specs applied, `pytest` 5/5 — but the run hit the runner's 30-minute
  per-run cap: after 63 conversations (one per action) the loop was still
  cycling (the last brief still planned to re-read the specs) and had not
  produced a bare `FINAL ANSWER` turn. Peak context and action counts for that
  row are therefore not measured (0 in `results.json`), and its `exit_code` is
  `timeout`. This is the expected SAC failure mode showing up: with a reset
  after every single action, a multi-step task can complete its work but fail
  to converge to termination within budget.
- **eocc ≈ fha here.** No task pushed eocc past the 18K-token compaction
  threshold (peaks ≤ 3.8K), so its rows are behaviorally identical to fha;
  eocc's reset path was exercised only in dry-run. The multi-session regime
  was materially tested by sac (2–9 compactions per run), which carried the
  staged-release state across resets via the handoff brief (or disk).
- **selective reading worked in all regimes.** find-needle-log (1.5 MB /
  ~20k-line log, far over any context budget) passed with peaks ≤ 1.7K tokens —
  the agent grepped and read a bounded window instead of the whole file.
- **Batch durability.** A first attempt at the exact same command lost 7 of 15
  runs to transient endpoint errors (rate limit / overload kill the run — the
  harness previously had no retry). The committed harness retries transient
  API errors with backoff; the numbers above are from the post-patch batch.
  Accuracy across the three regimes on this small suite is flat at 5/5, with
  sac's peak contexts comparable to fha's.
